# derive-sync 架构方案

> 版本：v0.1（2026-10）｜适用场景：个人 / 小团队自建，多设备（Windows、Linux、Android、iOS、macOS）互联
> 关联文档：[协议规范](protocol.md) ｜ [桌面平台调研](platform-desktop.md) ｜ [移动端平台调研](platform-mobile.md)

## 1. 一句话方案

一个**自托管中继 + 全端 SDK** 的端到端加密同步系统：中继服务器只做"电话交换机"（设备注册、配对转发、密文转发），**不存储也不解密任何内容**；剪切板、软件目录、文件本体全部在设备之间加密直传；软件目录只同步元数据，软件本体留在持有设备本地，需要时按需点对点中转；可选把加密数据暂存云端 30 天，到期强制删除；移动端不依赖常驻后台连接，用系统推送唤醒 + 拉取 + 用户确认的降级链路实现同等能力。

## 2. 需求拆解与硬约束

| # | 需求 | 设计响应 | 硬约束/现实限制 |
|---|---|---|---|
| R1 | 多设备互联，Windows/Linux/Android/iOS | Rust 核心协议全端复用；桌面原生常驻进程，移动端原生 App | iOS 无法后台常驻连接/静默读剪贴板；Android 10+ 后台禁读剪贴板 |
| R2 | 多设备共用剪切板 | E2E 加密的剪切板事件广播给所有已配对在线设备；文本/富文本/图片/文件占位四类 | 敏感内容（密码）必须 OS 层排除；大内容走文件中转 |
| R3 | 共享软件目录表，软件不上传服务器 | 目录仅同步元数据（名称/版本/平台/大小/BLAKE3）；本体按需设备间直传，中继只转密文分块 | 双方需同时在线；离线时走可选 30 天暂存或等上线 |
| R4 | 云服务器只做桥梁、不存内容 | 转发内容全部 E2E 加密、内存转发、不落盘；日志脱敏 | 中继仍可见元数据（设备 id、在线状态、大小、时间） |
| R5 | 可选云端存储，30 天后删除 | 客户端加密后上传密文；服务端 TTL clamp ≤ 30 天 + 60s 清理任务 + 启动清理；密钥只在设备端 | 到期删除不可恢复；单对象原型 8 MiB |
| R6 | 设备可选择共享的数据 | 每设备/每类型开关（文本、图片、文件、目录、暂存）；暂停同步热键；敏感来源排除 | 需各平台补齐"排除密码管理器"等系统集成 |
| R7 | 不同设备不同处理方式 | 能力矩阵 + 平台适配层（见 §10、platform-*.md） | 移动端是"推送→拉取→确认"而非无感同步 |
| R8 | 剪切板首次绑定需配对，后续默认配对 | 一次性 8 位码/二维码 + 6 位 SAS 防 MITM；配对后保存 PairRecord，自动重连认证 | 中继不可信，必须带外认证 |
| R9 | 保活与功耗 | 桌面：事件驱动 + 30s 心跳；移动：APNs/FCM 推送唤醒，无常驻连接；休眠/唤醒感知 | 推送不保证送达，需最终一致性兜底 |
| R10 | 低延迟、性能 | 局域网直连优先（v0.2）、WAN 走就近中继、剪切板去抖 100ms、zstd 压缩、分块流控、JSON→CBOR/二进制优化路线 | 中继转发多一跳，跨洲 RTT 是物理下限 |

**规模假设**：单用户/小团队，1 个中继，2~20 台设备，目录 ≤ 数千条，单文件 ≤ 数 GB，剪切板 ≤ 32 MiB（超大走文件中转）。

**组件职责**

| 组件 | 职责 | 不做什么 |
|---|---|---|
| Relay 中继 | 设备注册/presence、配对路由、密文转发、可选密文暂存与 TTL 清理、健康检查 | 不解密、不落盘转发内容、不持久化目录/剪切板/文件、不做业务逻辑 |
| Device 客户端 | 身份与配对、E2E 会话、剪切板监听/应用、目录 CRDT、文件分块传输、本地 spool、平台 UI | 不把明文内容交给中继；不依赖中继做一致性判断 |
| Push（可选） | 移动端唤醒信号（不含内容） | 不传内容、不作为唯一可达路径 |
| 反向代理 | TLS 终止、限流、wss 升级 | 不缓存请求体 |

## 4. 核心设计决策

| 决策 | 选择 | 理由 | 代价 |
|---|---|---|---|
| 信任模型 | 中继不可信，全链路 E2E | 自建 VPS 仍可能被入侵/运维窥探；软件分发涉及隐私 | 中继无法做服务端搜索/去重/内容审核 |
| 加密 | 每对设备连接级 X25519 ECDH + XChaCha20-Poly1305；配对用 SAS | 简单、成熟、连接级前向保密；避免一次性上 Double Ratchet 的复杂度 | 无消息级前向保密；v1.0 升级 Double Ratchet + 后量子混合 |
| 拓扑 | pairwise mesh（两两配对），无群组密钥 | 个人 2~20 台设备，N-1 条配对可控；避免群钥分发/轮换复杂度 | 设备多时握手数量 O(N²)；跨设备广播需 N-1 次加密发送（小规模可接受） |
| 配对 | 8 位码/二维码 + 6 位 SAS + 120s TTL | 中继不可信时防 MITM；二维码作为带外信道 | 需要用户在两端比对/扫码 |
| 目录 | 仅元数据 + HLC LWW-Map + 墓碑 | 软件本体留在本地是核心需求；CRDT 支持离线合并 | 无强一致；极端时钟偏差下 LWW 可能"旧写覆盖新写"（HLC 已缓解） |
| 本体中转 | 设备间 E2E 分块流式传输（中继转发密文） | 中继零存储；可断点续传；大文件不压中继磁盘 | 双方需在线；跨 NAT 依赖中继带宽 |
| 云端暂存 | 客户端随机密钥加密 + 服务端 TTL；密钥经 E2E 分享 | 服务端零知识；30 天强制删除满足需求 | 原型单对象 8 MiB；到期不可恢复 |
| 桌面传输 | WebSocket over TLS（wss） | 穿透 NAT/防火墙好、实现简单、可反向代理 | 头部开销；v0.2 加 QUIC 直连 |
| 移动传输 | 前台 wss/HTTP；后台推送+拉取 | iOS/Android 后台限制决定了没有别的选择 | 同步非实时（秒~分钟级），需产品预期管理 |
| 序号/去重 | E2E seq 严格递增 + event_id LRU + HLC | 防重放、防重复应用、离线补发幂等 | 严格有序要求单连接顺序传输（中继保证 FIFO） |

## 5. 关键数据流

### 5.1 首次配对（一次性，之后默认信任）

```
A 端                                Relay                          B 端
 │ 1. 生成本地身份+临时密钥            │                              │
 │    显示二维码/8位码                │                              │
 │── pair_announce(code_hash, invite) ─►│                             │
 │                                    │◄── 2. 用户输入码/扫码         │
 │                                    │    pair_join(code_hash, join)│
 │◄──── pair_event(join) ─────────────│──── pair_event(invite) ─────►│
 │ 3. 双方算 SAS（X25519+码+身份）     │                              │
 │ 4. 用户比对两端 SAS（或扫码即确认）  │                              │
 │ 5. 保存 PairRecord（对端公钥+指纹）  │                              │
 │ 6. 之后重连：session_init/ack 自动认证，无需再次配对                │
```

### 5.2 剪切板同步（桌面在线）

```
A: 用户 Ctrl+C
  → OS 事件/轮询检测（100ms 去抖）
  → 规范化 ClipboardPayload（text/image）+ BLAKE3 + zstd（>2KB）
  → 记录 last_local_hash；对每个在线已配对设备：
       PeerMessage::Clipboard{event}
       → E2E 会话加密 → relay{to, envelope} → B
B: relay → E2E 解密 → event_id 去重 → payload.verify_integrity()
  → 应用前检查 recent_applied（防回环）→ 写剪贴板
  → 写剪贴板会触发 B 本地监听，但 hash 命中 recent_applied → 忽略，不再广播
离线设备：事件进 spool（≤100 条/16MiB/24h），上线后补发
移动端：见 §5.6
```

### 5.3 软件目录同步

```
A 添加软件：catalog add → 计算 BLAKE3 / size / 平台 → 生成 CatalogEntry(hlc)
  → 写 catalog.json + local_index.json（entry_id → 本地路径）
  → 广播 CatalogDelta（E2E）
B: 收到 delta → CRDT 合并（HLC 大者胜）→ 持久化 → UI 列表可见
会话建立时：双方互发 CatalogSnapshot（含墓碑，<1MB）保证最终一致
可用性：双方广播 HaveList（本机持有哪些 entry 本体）
```

### 5.4 软件本体中转（核心诉求：云端不存内容）

```
B 在目录里看到 A 有软件 X，点击"获取"
B → A: FetchRequest{entry_id}
A: 查 local_index → FileChunker 计算清单（大小/BLAKE3/分块）
A → B: TransferOffer{manifest}
B: 校验清单 → 创建 incoming/.part → TransferAccept{from_offset=0}
A → B: TransferChunk × N（窗口 32 块/2MiB）
B → A: TransferAck（每 8 块/512KiB）
A → B: TransferDone
B: 校验整体 BLAKE3 → 原子重命名 → 更新 local_index + 目录
全链路：A→中继→B 均为 E2E 密文；中继不落盘、不缓存
断线：B 保留 .part，重连后 from_offset 续传
```

### 5.5 可选云端暂存（30 天 TTL）

```
A: vault put 文件 → 随机 object_key → XChaCha20-Poly1305 加密
  → 本地保存 object_key（vault_keys.json）
  → vault_put{object_id, meta, ciphertext, ttl_secs}
Relay: TTL clamp ≤ 30d → 写入 vault_dir/<id>.bin + index.json
  → 60s reaper + 启动清理，到期物理删除
A → 已配对设备: VaultShare{object_id, key} (E2E，离线排队)
B: 拿到 key → vault_get → 解密 → 校验 BLAKE3
```

### 5.6 移动端（推送唤醒 + 拉取 + 用户确认）

```
桌面 A 复制/发送文件
  → relay: A 在线；若 B 移动端离线/后台
  → 若配置了推送：relay 向推送服务发送"有更新"信号（不含内容，仅 object 提示）
  → B 收到 APNs/FCM 唤醒 → 短连接 HTTPS 拉取密文 → 本地解密
  → Android: 后台可写剪贴板 → 直接写入（可选自动）/通知
  → iOS: 通知栏展示 → 用户点按/打开 App → UIPasteControl/确认后写入剪贴板
  → B 主动分享：分享面板/快捷指令/前台复制 → 上传密文到 relay → A 拉取
```

> 结论：移动端不是"无感双向同步"，而是"可预期的异步同步"。这是平台限制，不是实现缺陷；产品文案必须提前说明。

## 6. 延迟与性能

### 6.1 延迟预算（目标）

| 场景 | 目标 | 说明 |
|---|---|---|
| 同 LAN 直连（v0.2） | p95 < 20ms | mDNS + QUIC，无中继 |
| 同城 VPS 中继 | p95 < 150ms | 一跳：A→VPS→B + 加密/解密/序列化 |
| 跨洲中继 | p95 < 400ms | 物理 RTT 主导，可接受 |
| 移动端推送唤醒 | 秒~分钟级 | 受 iOS/Android 推送策略限制，不承诺实时 |
| 软件本体传输（LAN） | ≥ 50 MB/s | 直连 + 64KiB 块 |
| 软件本体传输（WAN 中继） | ≥ 5 MB/s | 取决于 VPS 带宽，原型 JSON+base64 有约 1.7x 开销 |

### 6.2 优化手段（已实现 / 计划）

| 手段 | 状态 |
|---|---|
| 剪切板去抖 100ms、变化哈希去重 | v0.1 |
| zstd 压缩（>2KB，收益 >5% 才用） | v0.1 |
| 64 KiB 分块 + 32 块流控窗口 | v0.1 |
| 中继帧率限速 2000 帧/s（≈125 MiB/s）+ 令牌不足背压等待（不丢块） | v0.1 |
| 事件驱动（不轮询网络）；轮询仅桌面剪切板本地检测 | v0.1 |
| 中继内存转发、零磁盘 IO | v0.1 |
| JSON+base64 → 二进制帧/CBOR（吞吐 +30~40%） | v0.2 |
| LAN mDNS + QUIC 直连 | v0.2 |
| 按字节限速（数据帧 byte/s + 控制帧 frame/s），替代纯帧数限速 | v0.2 |
| 多路复用/批处理目录增量 | v0.2 |
| 中继就近部署 + 同一区域多节点 | 运维层 |

### 6.3 性能测量方法

- `derive-bench`：进程内启动中继 + 两台虚拟设备，测 E2E 加密转发 RTT 的 p50/p95/p99、吞吐（不同 payload 大小）。
- 真实双机 LAN/WAN 测试：记录复制→对端可用时间、大文件吞吐、CPU/内存/电量。
- 指标埋点（生产）：同步成功率、p95 延迟、重连次数、spool 深度、中继带宽。

## 7. 保活与功耗

| 平台 | 连接策略 | 唤醒/保活 | 功耗控制 |
|---|---|---|---|
| Windows | 托盘常驻，wss 长连接 | WS ping 30s；TCP keepalive；休眠/唤醒事件（WM_POWERBROADCAST）恢复后立即重连 | 事件驱动剪切板监听（AddClipboardFormatListener）+ 空闲时无定时器；心跳定时器合并 |
| Linux | systemd user service，wss 长连接 | ping 30~45s；logind PrepareForSleep 处理 | X11 XFixes / Wayland wl-paste --watch 事件驱动；无轮询 |
| Android | 无常驻连接 | FCM 高优先级 data message（仅唤醒，1 次 HTTPS 拉取）；WorkManager 周期兜底（≥15min） | Doze 友好：不申请 FGS 常驻；传输时才用前台服务；短连接结束即释放 |
| iOS | 无常驻连接 | APNs（alert 优先保证可达；background 仅兜底，不保证送达）；BGTaskScheduler 兜底 | 无后台 socket；30s 后台窗口内完成拉取；不轮询 |
| 全部 | 断线退避 1s→30s ±20% 抖动 | 唤醒/网络切换后立即重连一次 | 指数退避防雪崩；批量/压缩减少流量 |

**心跳参数**：桌面 WS Ping 30s（NAT 保活通常 60~120s 足够，30s 属保守值，可配置）；空闲超时 90s；应用层 PeerMessage Ping 仅在需要探测链路时使用，避免额外功耗。

**移动端现实**：系统会在锁屏/低电量时冻结进程；任何"常驻后台同步"的方案都会失败或被杀。正确做法是把"实时性要求"降级为"可接受的异步"，并用推送+通知保证用户感知。

## 8. 安全与隐私

### 8.1 威胁模型

| 威胁 | 缓解 |
|---|---|
| 中继被入侵/运维窥探 | E2E 加密；中继仅见密文与元数据；暂存也只存密文 |
| 中继主动 MITM | 配对 SAS/二维码带外认证；会话握手用配对身份密钥签名验证 |
| 重放/乱序 | E2E 方向序号严格递增；event_id LRU |
| 伪造设备注册 | Hello Ed25519 签名 + device_id 一致性校验 + access token |
| 配对码暴力破解 | 8 位数字 + 120s TTL + 失败即销毁 + 5 次/分钟限流 |
| 设备丢失 | 删除本地 PairRecord（对端拒绝会话）；v1.0 支持远程撤销 + 密钥轮换 |
| 云端暂存泄露 | 客户端随机密钥加密，服务端无密钥；TTL ≤30d |
| 剪切板敏感内容外泄 | OS 层排除密码管理器；按类型/设备开关；一键暂停；不落日志 |
| 目录元数据泄露 | 目录内容 E2E 加密；中继不可见；暂存 meta 生产可再加密 |

### 8.2 加密原语

- 身份：Ed25519（签名）+ X25519（密钥交换）。
- 配对：X25519 ECDH + HKDF-SHA256 + 6 位 SAS。
- 会话：连接级临时 X25519 ECDH + HKDF-SHA256，XChaCha20-Poly1305（随机 24B nonce，AAD 绑定版本/会话/序号/类型/时间）。
- 云暂存：每对象随机 32B 密钥 + XChaCha20-Poly1305，AAD=object_id。
- 内容完整性：BLAKE3（剪切板载荷、文件、目录内容哈希）。
- v1.0 计划：Double Ratchet（消息级前向保密）+ X25519/ML-KEM 混合（抗量子）、密钥轮换、设备撤销广播。

### 8.3 隐私默认值

- 剪切板默认只同步文本；图片/文件需显式开启。
- 目录默认分享元数据；软件本体永不自动上传。
- 云端暂存默认关闭；开启时默认 TTL 24h、上限 30d，敏感条目禁止入云。
- 密钥、令牌不入日志；`identity.json` 0600；移动端放 Keychain/Keystore。

## 9. 数据模型（本地）

```
identity.json    设备 Ed25519+X25519 密钥、名称、创建时间（0600）
peers.json       PairRecord[]：对端 PublicIdentity、relay_url、配对时间、指纹
config.json      relay_url/token、剪切板策略、spool 限额、暂存开关
catalog.json     CatalogEntry Map（含墓碑）+ node
local_index.json entry_id → 本地文件路径 + content_hash（仅持有设备）
vault_keys.json  object_id → 32B 密钥（云暂存解密用）
spool/           待发 PeerMessage（离线补发，TTL/限额）
incoming/        .part 接收中文件 + 已收文件
```

关键约束：

- 目录条目与本地路径解耦（换机/移动文件不影响目录一致性）。
- 删除是墓碑（30 天后 GC），防止离线设备复活旧条目。
- 所有 JSON 原子写（tmp + rename），崩溃不损坏。
- 服务器（中继）只有连接态、配对登记（TTL）、暂存索引（密文 + 元数据）。

## 11. 可靠性设计

| 故障 | 处理 |
|---|---|
| 中继重启 | 客户端指数退避重连；重连后重建会话、重发 snapshot/have_list/spool；中继不丢内容（本来就无内容） |
| 设备休眠/断网 | 检测系统唤醒/网络变化立即重连；离线期间事件进 spool（≤100 条/16MiB/24h） |
| 重复消息 | event_id LRU 去重；目录 CRDT 幂等；传输 transfer_id 幂等 |
| 传输中断 | .part 保留，重连续传；校验失败删除重传 |
| 目录冲突 | HLC LWW；同 HLC 不同内容记 conflict 并保留本地，日志告警 |
| 崩溃 | 原子写 + 启动时清理过期 .part/spool；身份文件损坏则提示重新配对 |
| 配额超限 | 中继返回明确错误码；客户端提示并保留本地副本（暂存到期前） |
| 时钟偏差 | HLC 保证逻辑单调；LWW 冲突概率低；关键场景以内容哈希为准 |

## 12. 部署与运维（自建）

最小部署：

```
VPS (1C1G 起) 或 NAS
  ├─ Caddy/Nginx：TLS 证书、wss 反向代理 → 127.0.0.1:8787
  ├─ derive-relay（单二进制）：--bind 127.0.0.1:8787 --access-token <强随机>
  ├─ vault 目录：仅密文，磁盘配额/备份策略按需
  └─ /healthz 探活 + 日志（脱敏）
```

建议：

- 中继部署在离常用设备近的区域（同城/同区域），跨洲延迟主要来自光速。
- access_token 用 32B 随机生成；只发给自己的设备；泄露即轮换并重启中继。
- 反向代理限制请求体大小（略大于 8 MiB）、超时 > 120s（大文件块）、禁用缓存。
- 暂存目录单独挂载/限额；定期审计对象数与配额。
- 中继不备份内容（无内容可备份）；只备份 access_token/配置。
- 监控：在线设备数、连接数、转发帧数/字节、暂存对象数/字节、过期删除数、错误率。
- 升级：中继与客户端协议版本兼容窗口 ≥ 1 个大版本；破坏性变更升 `PROTOCOL_VERSION`。
- Docker：`docker run -v /data/derive:/data -e DSYNC_TOKEN=... derive-relay --vault-dir /data/vault`

## 14. 风险与开放问题

1. **iOS 期望落差（最高风险）**：无法做到"复制即同步、后台静默粘贴"，用户会拿 Universal Clipboard 对比。需要在产品文案与首次引导中明确说明。
2. **移动端推送可靠性**：FCM 降级/APNs 静默推送限流、国内无 GMS 设备 FCM 不可用；需要厂商推送（MiPush/HMS/OPPO/vivo）方案 + 前台/手动兜底。
3. **NAT 穿透与直连**：对称 NAT/企业网下仍会回落到中继；QUIC 打洞成功率需实测。
4. **中继带宽成本**：大文件中转消耗 VPS 流量；自建小水管会成为瓶颈，需限速/提示走 LAN。
5. **敏感剪切板**：密码管理器格式排除依赖各平台系统集成，需要逐平台测试。
6. **时间/时区/时钟偏差**：HLC 已缓解 LWW 冲突，但用户手工改系统时间仍可能产生异常顺序。
7. **30 天暂存的合规**：即使服务端只存密文，仍可能被认定为处理个人信息/数据；需按 docs/platform-mobile.md 的合规清单在目标地区评估。
8. **跨设备全互通**：v0.1 只与已配对设备同步；A-B、B-C 配对时 A、C 不互通，需要两两配对或后续群组转发。
